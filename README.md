## 2. Обґрунтування захищеної ознаки та аналіз проксі-ознак (п. 5.2)
* **Захищена ознака:** `AccountWeeks` (тривалість користування сервісом у тижнях). Вона виступає аналогом «віку» клієнтського профілю. Її використання безпосередньо створює ризик дискримінації нових абонентів на користь давніх клієнтів (або навпаки). Ознака прямо присутня в наборі даних.
* **Архітектурне виключення:** Ознаку повністю виключено з блоку `features` та поміщено у `protected_attributes`. Будь-яка спроба випадкового додавання цієї колонки до простору ознак перехоплюється функцією `validate_config` ще до етапу збирання графу обчислень.
* **Аналіз проксі-ознак:** Ознака `ContractRenewal` потенційно корелює з тривалістю життя акаунту, але її залишено у `features`, оскільки вона відображає прямий поведінковий намір клієнта розірвати договір і має вирішальну предиктивну цінність.

## 3. Обґрунтування схеми ключів model_family (п. 3.4.4)
Обрано рекомендовану дихотомію **`additive / partitioning`**:
* **`additive` (адитивні моделі, наприклад, Logistic Regression):** Комбінують ознаки у лінійну зважену суму ($w^T x$). Вони чутливі до одиниць вимірювання та асиметрії розподілів, тому вимагають обов'язкового масштабування (`standard_scaler`) та стабілізації дисперсії (`log1p`).
* **`partitioning` (розбиваючі моделі, наприклад, Decision Tree / Random Forest):** Розбивають простір ознак пороговими предикатами. Вони інваріантні до будь-яких монотонних перетворень, що зберігають порядок значень (множення на константу чи логарифмування не змінює положення спліту). Тому шкалювання для них є зайвою операцією, а для захисту від викидів застосовується `winsorize`.

## 5. REFORMS-аудит (Блоки 1–2)

### Модуль 1. Цілі дослідження
* **1a (Популяція):** Абоненти телекомунікаційного оператора зі сформованою історією користування голосовими та інтернет-послугами.
* **1b (Обґрунтування):** Популяція визначена структурою відкритого набору даних Telecom Customer Churn Dataset.
* **1c (Обґрунтування ML):** Зв'язок між кількістю дзвінків у підтримку, сумою рахунку та схильністю до відтоку є нелінійним і взаємопов'язаним. Використання складніших ML-моделей є виправданим лише за умови перевищення метрик бейзлайну (Recall > 0.5300 при прийнятній точності).

### Модуль 2. Обчислювальна відтворюваність
* **2a (Дані):** Telecom Customer Churn Dataset (Kaggle), 3333 записи.
* **2b (Код):** Фіксується хешем коміту в системі контролю версій Git.
* **2c (Середовище):** Python 3.12, залежності зафіксовані у `requirements.txt` (`pandas`, `scikit-learn`, `pyyaml`, `numpy`).
* **2d (Документація):** Інструкція запуску: `pip install -r requirements.txt` → `python run_verification.py`.
* **2e (Детермінованість):** Усі кроки побудови конвеєра та препроцесингу є повністю детермінованими. Класифікатори не навчаються, псевдовипадкові генератори не використовуються. Параметр `random_state` з'явиться вперше в Лабораторній роботі №2 під час розбиття на train/test.
